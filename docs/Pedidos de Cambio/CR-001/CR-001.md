# CR-001 — La validación actual es parcial y no garantiza datos válidos

El proyecto ya usa `react-hook-form` con esquemas Yup en la mayoría de los formularios de datos de negocio, y muestra errores de campo y errores generales de API. Sin embargo, **CR-001 todavía no está cumplido**: hay formularios anidados cuya validación no participa del guardado principal, selectores que aceptan `0` como identificador válido, formatos críticos validados sólo por máscara o teclado y mensajes de error con tratamiento inconsistente.

## Alcance revisado

Se revisaron formularios de:

- organización: clientes, proveedores, personal, condiciones de IVA, localidades y domicilios;
- productos: marcas, líneas, sublíneas, productos, proveedores asociados y productos alternativos;
- precios e importaciones: cambio manual, IVECO, NEX-PRO y carga de archivos;
- componentes reutilizables de documentos, importes y selección de productos.

Quedaron fuera de alcance, según lo solicitado, autenticación, cuentas/usuarios, configuración interna del sistema y campos usados sólo para búsqueda o filtrado.

## ¿Qué es un esquema Yup?

Un esquema Yup es una **declaración centralizada de las reglas que deben cumplir los datos** antes de considerarse válidos. Para cada campo define su tipo, obligatoriedad, formato, longitud, rango y mensaje de error. También puede expresar reglas condicionales o relaciones entre campos.

Por ejemplo:

```ts
const schema = yup.object({
  denominacion: yup
    .string()
    .trim()
    .required("La denominación es obligatoria.")
    .max(255, "Máximo 255 caracteres."),
  precio: yup
    .number()
    .typeError("El precio debe ser numérico.")
    .min(0, "El precio no puede ser negativo.")
    .required("El precio es obligatorio."),
});
```

En este proyecto, `yupResolver(schema)` conecta Yup con React Hook Form. Cuando una operación pasa por `handleSubmit`, React Hook Form ejecuta el esquema: si los datos son válidos llama a `onSubmit`; si no lo son, bloquea el envío y expone los mensajes mediante `formState.errors`.

El esquema es la **fuente de verdad de la validación del formulario**. Una máscara, el tipo HTML del input o un filtro de teclado sólo ayudan a ingresar datos; no reemplazan al esquema. Además, el esquema no protege por sí solo si un botón, callback o formulario anidado evita `handleSubmit`. Por eso las reglas también deben validarse en el backend antes de guardar.

## Evaluación por grupo

### Con una base de validación adecuada

- **Marca, línea, sublínea, condición de IVA, localidad, personal y producto:** ya usan Yup y bloquean el `onSubmit` principal cuando el esquema falla.
- **Producto:** valida costo/precio, porcentaje, relaciones obligatorias y reglas condicionales de stock/pack.
- **Cambio manual de precios:** exige números no negativos.
- **Importaciones IVECO/NEX-PRO:** validan la cotización y la existencia de un archivo.
- **Ítems proveedor/producto alternativo y sublíneas:** ejecutan `trigger()` antes de agregar el ítem y controlan duplicados.

Esta base debe conservarse, pero necesita las correcciones de la tabla anterior. En particular, “tener un schema” no garantiza nada si la operación que agrega o guarda no pasa por ese schema.

### Regex: dónde corresponde y dónde no

Usar regex para **estructura textual estable**, por ejemplo:

- prefijo de comprobante: `^\d{4}$` si la regla confirmada es exactamente cuatro dígitos;
- número de comprobante: `^\d{10}$` si la regla confirmada es exactamente diez dígitos;
- DNI: sólo dígitos y longitud definida por negocio;
- teléfono: caracteres permitidos, después de normalizar.

No usar regex como solución principal para precios, cantidades, IDs, rangos, fechas ni CUIT. Esos campos requieren validadores tipados y, para CUIT, una comprobación algorítmica.

## Manejo actual de errores

Aspectos positivos:

- los inputs reutilizables muestran el mensaje de Yup junto al campo;
- los formularios principales capturan errores de API con `parseApiError` y los muestran como error `root`;
- los botones de guardado suelen deshabilitarse durante `isSubmitting`.

Mejoras necesarias:

1. **Asociar visual y semánticamente cada error al campo:** borde/estado inválido, `aria-invalid`, `aria-describedby` e identificador estable del mensaje.
2. **Enfocar el primer campo inválido** y agregar un resumen visible al intentar guardar, especialmente en formularios largos. Actualmente `FormInput` reemplaza la referencia de React Hook Form, incluso por `undefined` cuando no recibe una referencia externa, lo que puede impedir el foco automático.
3. **Usar `role="alert"` o una región `aria-live`** para errores generales y de carga.
4. **Mapear errores de validación del backend al campo correspondiente** cuando la API devuelva información estructurada; reservar `root` para errores globales.
5. **Evitar fallos silenciosos:** varias búsquedas y cargas auxiliares sólo escriben en consola o ignoran el `catch`. Mostrar un mensaje accionable y permitir reintento.
6. **Unificar textos:** indicar qué campo falló, qué formato/rango se espera y conservar una terminología consistente. Corregir mensajes cruzados existentes (por ejemplo, reglas de marca/línea o “precio sin IVA” para un campo llamado `precioConIva`).
7. **Limpiar errores generales obsoletos** al reintentar o modificar el dato que los originó.

## Solución propuesta

1. Crear validadores reutilizables para ID positivo, texto normalizado, código de negocio, teléfono, DNI, CUIT y número de comprobante.
2. Componer un único esquema por operación de guardado. Los componentes anidados deben compartir el formulario padre o exponer una API de validación obligatoria.
3. Ejecutar la validación completa justo antes de construir el payload y bloquear el servicio si existe cualquier error.
4. Mantener máscaras, restricciones de teclado y atributos HTML (`inputMode`, `maxLength`, `accept`) como ayudas de entrada, nunca como única defensa.
5. Estandarizar la presentación accesible de errores en `FormInput`, `PriceInput`, `CantidadesInput`, `EmailInput` y selectores.
6. Validar nuevamente en backend con las mismas reglas de dominio; el frontend mejora la experiencia, pero no es una frontera de confianza.
7. Agregar pruebas unitarias de los esquemas/validadores y pruebas de integración que demuestren que una operación inválida no invoca al servicio.

## Criterios de aceptación sugeridos

- [ ] Ningún botón de agregar/guardar llama a callbacks o servicios si el formulario completo es inválido.
- [ ] Todo ID seleccionado es un entero válido mayor que cero o pertenece al catálogo esperado.
- [ ] CUIT, DNI y números de comprobante se validan después de normalizar, incluido pegado de texto.
- [ ] Fechas, importes, porcentajes y cantidades respetan rangos de negocio y rechazan valores no finitos.
- [ ] Archivos inválidos se rechazan antes de importar y el backend repite la validación.
- [ ] Cada error de campo es visible, accesible y específico; los errores globales no reemplazan errores de campo.
- [ ] Los errores de API conocidos se asignan al campo correspondiente y los desconocidos conservan un mensaje general seguro.
- [ ] Existen pruebas que verifican tanto aceptación de valores límite válidos como rechazo de inválidos.
